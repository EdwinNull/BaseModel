## 0 一页结论

- **定位变了**：flucase 原来是"病例标准化与复核系统"——研究者用，真实数据要先对齐成 CDM v3.1，医生只做复核。改为**多中心老年流感病例数据收集系统**：医生把本院导出的 Excel 导入系统，系统把它读成统一的病例记录，告诉医生读到了什么、哪里要处理；分级、复核、质控、导出保留，作为病例库之上的研究者功能。
- **要改三件事**：
  1. **导入去掉对齐。**每种格式一个读取器，直接把 Excel 读成病例记录；不再调用服务器对齐代码，不生成 CDM v3.1，不用化名对照表。GD式、GAM式住院、GAM式门诊每个文件都能单独导入（现在必须三个一起）。
  2. **以病例库为中心。**导入是累加的（新增 / 更新 / 不变），每个值都能追溯到"哪个文件、哪张表、第几行、哪一列、原值是什么"；每次导入可以撤销；医生可以更正，原值保留。取代现在"同一来源再导入就替换上一次"的做法。
  3. **医生端重做。**导入分四步：选文件 → 认格式 → 看读到了什么 → 确认导入。每次导入都给一份回执：导入了多少、哪些没导入及原因、要你处理什么。问题清单精确到行和列，医生页面上不出现 CDM、批次、运行、映射字典、规则集、化名这类词。
- **为其他中心打基础**：内置格式写成"格式族读取器 + 格式配置"，按表头文字和编码找列，不依赖固定列号。与 GD式、GAM式相似的文件（列顺序、列名、工作表名不同，或少几列、多几列）在页面上确认差异，存成新格式就能用，不用改代码。认不出的文件走格式向导（现在的通用导入）；实在对不上的中心，用系统按数据字典生成的标准导入模板。
- **不变的**：医院数据不发给任何在线大模型或 API（含 Claude）；Claude 不读真实病例，开发和测试只用虚构数据；真实数据不进任何代码仓库；分级口径等 A 档决策仍归研究者（§8）。
- **时间（估计）**：最小可用版本（GD式、GAM式单文件导入 + 预览 + 回执 + 问题清单 + 病例详情 + 撤销）约 3 周，11 月初可以请医生试用；全部阶段约 5–6 周，赶在 12 月流感高峰之前。

## 1 研究者 10-14 的要求与本规划的理解

### 1.1 四点要求

| # | 要求 | 本规划怎么落实 |
|---|---|---|
| 1 | 医生清楚怎么操作、操作后得到了什么 | §4：导入向导、回执、问题清单、病例详情、导入记录；用语规范；可用性测试（§6.3） |
| 2 | 不做对齐，系统本来就是医生导入、收集数据用的 | §1.2、§3：读取器直接读成病例记录，病例库累加 |
| 3 | 不考虑服务器和两台本机之间的数据隐私 | §1.3：系统内去掉化名、文本清洗、隐私审计拦截、小格抑制 |
| 4 | 先做 GD式、GAM式及类似 Excel，为其他中心打基础 | §3.4、§3.5：格式族 + 格式配置 + 相似格式 + 格式向导 + 标准模板 |

### 1.2 "不做对齐"指什么

**不再做**：

- 调用服务器对齐代码（`flucase/pipeline/legacy/`，经 `flucase/align` 包装）；
- 生成 CDM v3.1 目录、补 SHA256SUMS、与服务器 CDM 逐文件核对（`python -m flucase.align compare / verify`）；
- 化名对照表，以及"对齐代码先编化名、包装层再换回病例ID"（D37 的做法）；
- 要求 GD式、GAM式住院、GAM式门诊三个文件一起导入；
- 为"GAM 训练、GD 测试"做的跨院派生（`legacy/derive.py` 的 `crf_view`、`outcome_components`、候选列）——这是实验侧的事，不放在收集系统里。

**仍然要做**（叫"读取"，医生看到的说法是"导入"）：把每种格式读成同一种病例记录——同一个数据项（体温、白细胞……）用同一个编码和单位，时间带精度，每个值带来源单元格。没有这一步，多个中心的数据放不进同一个病例库，也没法分级和导出。这是任何收集系统都要做的读取，不是原来意义上"两院对齐"。

请研究者确认这个理解（§7 第 1 项）。

### 1.3 "不考虑隐私"在系统里意味着什么

| 现在的做法 | 改为 |
|---|---|
| 演示来源用 `DEMO-` 化名；真实数据先化名再换回病例ID（D37） | 病例ID 直接用医院编号（病案号、住院号、关联字段），按中心区分；不再需要两院同号时加的"@来源" |
| 病历文本清洗姓名、号码（对齐代码 `scrub_text`） | 不清洗，医生看到原文 |
| 运行的 S3 步骤做隐私审计，命中就停止（`pipeline/runner.py`）；对齐出错只给"报错类型 @ 代码位置"（`align._describe`） | 去掉审计拦截；问题清单直接给原值和行列号 |
| 映射预览、校验结果"只出计数，不出逐行内容" | 给真实示例值和具体位置 |
| 质控接口一律小格抑制（1–9 显示"<10"，`qc/suppress.py`） | 系统内显示实际数字；对外报告的导出里可选 |
| 上传的原始 Excel 导入后删除（对齐路径只留 CDM） | 原始文件归档保留，作为追溯和重读的依据 |
| 正式模式下 GD式、GAM式原始 Excel 不能单个上传（`RAW_USE_ALIGNMENT`） | 去掉，三种格式都能单个导入 |

另外几条不属于"研究者自己的设备之间"的问题，这次不变，见 §8。

## 2 现状审视（flucase `f657f04`）

### 2.1 现在的导入链路

```
导入页（只有管理员能进）有 5 个入口：
① 原始 Excel 三件套 ─► flucase/align ─► legacy.run_alignment（编化名、清洗文本、派生、写 CDM）
                    ─► 化名换回病例ID（D37）─► 数据区 aligned/<版本>/（CDM v3.1）
                    ─► CDM 适配器 ─► GD_CRF、GAM_IP、GAM_OP 三个批次 ─► 各跑一次 S1–S11
② CDM 目录 ───────────────────────────────► CDM 适配器 ─► 三个批次 ─► S1–S11
③ 单个文件：门急诊导出模板、已保存的格式 ─► 对应适配器 ─► 一个批次 ─► S1–S11
④ 单个文件认不出 ─► 通用导入（确认每列的含义、存成格式）─► 一个批次 ─► S1–S11
⑤ 虚构样例（GD 演示适配器、EHR 演示适配器、门急诊）
病例页 = 每个来源"最新完成的那次运行"
```

### 2.3 与新目标的差距

| # | 问题 | 在哪里 | 对医生的影响 |
|---|---|---|---|
| P1 | 原始 Excel 必须三个一起导入 | `align/__init__.py` 的 `pick()`；README 写明"对齐代码目前要三个文件一起导入" | GD 的医生手里只有 GD式文件，导不进去 |
| P2 | 链路绕四道：Excel → 对齐（化名、清洗、派生）→ CDM → 换回病例ID → CDM 适配器 | `align.run()`、`use_case_ids()` | 出错时不知道是哪一行；报错只有"类型 @ 代码位置" |
| P3 | 同一来源再导入就替换上一次 | `service.Workspace.current_runs`；`generic.py` 开头的说明 | 分月导入、几位医生分别导入时，前面的数据"消失" |
| P4 | 复核结论按抽取记录编号叠加，而 GD 演示适配器、通用导入的编号按出现顺序编 | `models.Override.ext_id`；`gd_crf.py`、`generic.py` 的 `nid()` | 重新导入后，判定可能挂错或丢失 |
| P5 | 对齐路径的原始 Excel 导入后删除，只留 CDM | `api/pipeline_api.py` 的上传清理 | 回不到原始单元格核对，也不能用改进后的读取器重读 |
| P6 | 预览和报错按"不出逐行内容"设计 | 映射预览只给统计量；`align._describe` | 医生看不到读成了什么、问题在哪 |
| P7 | 用语面向研究者；正式模式下仍显示"只含虚构数据""演示" | `views/ImportView.vue`；`layouts/MainLayout.vue` 侧栏；`router/index.ts` 的页面标题 | 医生看不懂；正式环境写"只含虚构数据"是错误信息 |
| P8 | 导入、病例两页只给管理员；医生（录入员）只能做前瞻录入 | `router/index.ts`、`config/nav.ts` | 医生不能自己导入、看本院病例 |
| P9 | GD 演示适配器靠固定列号（102 列），只读 4 种并发症，不读病程文本 | `adapters/gd_crf_schema.py`、`gd_crf.py` | 列顺序不同或增删列的 CRF 会错位 |
| P10 | 没有"更正"，只能等复核条目 | — | 医生发现读错了没处改 |
| P11 | 没有导入记录和撤销 | — | 导错了文件撤不回 |
| P12 | GAM 门诊没有年龄、性别，要靠同一病人的住院补，现在只在三件套对齐里一次做 | legacy `gam_ehr._build_op` | 分开导入时门诊病例缺年龄、性别 |
| P13 | 导出绑定 CDM（std_v1 的对齐层）；没有给医生的整理后表格 | `export/std_v1.py` | 医生拿不到"整理好的表" |
| P14 | 服务只监听 127.0.0.1，靠 SSH 隧道访问 | README"配置" | 医生实际上用不上 |

### 2.4 三种做法的比较

| 做法 | 怎么做 | 好处 | 问题 | 结论 |
|---|---|---|---|---|
| 甲：在旧对齐上修补 | 改 legacy，让它能单文件跑、去掉化名 | 看起来改动少 | legacy 一改就失去"与服务器一致"的意义（而这个前提已经不需要）；仍要经过 CDM 中间层和派生列；报错仍不带位置；仍绑 pandas 2.x | 不推荐 |
| **乙：移植读取经验，写 flucase 自己的读取器** | GD式、GAM式各写读取器：按表头找列，单文件可导，直接产出病例记录和带位置的问题 | 链路短、能单文件、可解释；"相似格式"靠配置；legacy 验证过的规则一条不丢 | 要移植约 1500 行读取逻辑并补测试；要在真实数据上核对一次计数 | **推荐** |
| 丙：全部走通用导入 | GD式、GAM式也用通用导入向导 | 不用写代码 | 续行分组、表头错位、病历解析、门诊挂接都做不了，读出来的质量差 | 不推荐 |

## 3 目标形态

### 3.1 一句话与两条使用路径

**一句话**：医生上传本院导出的 Excel，系统认出格式、读成统一的病例记录，先给医生看读到了什么和哪里有问题，医生确认后进入病例库；研究者在同一个病例库上做分级、复核、质控和导出。

- **医生**：登录 → "我的中心"首页（已收集多少、上次导入、待处理问题）→ 导入数据（四步）→ 看回执 → 处理问题 → 浏览、更正病例 → 需要时下载本中心统一格式 Excel。
- **研究者**：管理中心与账号 → 格式库（新增、调整格式）→ 看全部中心的病例 → 分级、复核、质控 → 冻结与导出。

### 3.2 总体结构

```
医生上传 Excel
   │
   ▼
① 认格式（格式库：内置 / 已保存 / 相似 → 确认差异 / 认不出 → 格式向导或标准模板）
   │
   ▼
② 读取（格式族读取器 + 格式配置）→ 读取结果：患者、就诊、记录、病历、问题，全部带来源单元格
   │                                  （这一步不写病例库，只用于预览）
   ▼
③ 预览：读到了什么 + 和病例库比（新增 / 更新 / 不变）+ 问题（不能导入 / 请确认 / 提示）
   │ 医生点"确认导入"
   ▼
④ 合并进病例库：按（中心, 就诊编号）新增、更新（建新版本）或不变；原始文件归档；写导入记录和回执
   │
   ▼
病例库：有效值 = 复核结论 ?? 医生更正 ?? 导入值
   ├─► 挂接（门诊 ↔ 住院，补年龄性别、随访）
   ├─► 分级（病例有变化就自动重算）─► 复核、全字段标注
   └─► 质控、冻结、导出（std_v2、本中心统一格式 Excel）
```

### 3.3 病例库

**表**（应用库；开发用 SQLite，部署用 PostgreSQL）：

| 表 | 一行是什么 | 主要列 |
|---|---|---|
| 中心 `site` | 一个参与中心 | 代码、名称 |
| 导入 `import_job` | 一次导入 | 中心、导入人、时间、格式及版本、读取器版本、状态（预览中 / 已导入 / 已撤销 / 失败）、回执摘要 |
| 原始文件 `import_file` | 导入的一个文件 | 文件名、sha256、大小、归档位置、工作表清单 |
| 患者 `patient` | 中心内一位患者 | 中心、患者编号（病案号或病人ID，去前导零、字母大写）、姓名（§7 第 2 项）、性别 |
| 就诊 `encounter` | 一次住院或门急诊 | 中心、就诊编号、患者、场景（住院 / 门急诊）、当前版本 |
| 就诊版本 `encounter_version` | 某次导入读到的这次就诊 | 导入、内容指纹、入院 / 就诊时间（精度、取法）、出院时间、去向、年龄、科室 |
| 记录 `record` | 一个值 | 版本、类别（人口学 / 体征 / 检验 / 症状 / 基础病 / 治疗 / 诊断 / 并发症 / 影像 / 结局）、数据项编码、数值或文字、单位、三态与语境、时间与精度、结束时间、来源（文件、工作表、行、列、表头、原值）、标记、记录指纹 |
| 病历 `note` | 一份文书 | 版本、类型、书写时间与精度、正文、来源 |
| 问题 `issue` | 一个要处理的问题 | 导入、就诊（可空）、问题代码、级别、说明、位置、原值、系统怎么处理、建议、状态（待处理 / 已改 / 已确认 / 已忽略）、处理人与备注 |
| 更正 `correction` | 医生改的一个值 | 就诊、记录指纹、原值、新值、时间与精度、原因、人、时间、是否被取代 |
| 格式 `format` | 一种格式的一个版本 | 键、名称、格式族、版本、配置、基于哪个格式、状态（草稿 / 启用 / 停用） |
| 挂接 `link` | 门诊 → 住院等关系 | 两端就诊、规则、时间差 |

复核相关的表（批次、条目、判定、共识、覆盖值）保留，改为按"就诊 + 记录指纹"挂接。

**两种指纹**：

- **记录指纹** = 中心 + 就诊编号 + 类别 + 数据项 + 时间 + 来源位置（表格：工作表 + 表头；病历：文书类型 + 书写时间 + 规则号）。不含行号（医生在原表插行时行号会变），也不含取值。同一个单元格重新导入，指纹不变，所以更正和复核结论重导后还挂得上；原表的值改了也认得出来（"你更正过的这个值，原表也改了"）。
- **内容指纹** = 一次就诊全部记录（含取值）排序后的哈希，用来判定"不变 / 更新"。

**合并规则**（每次确认导入时执行；预览阶段先算一遍给医生看）：

| 情况 | 判定 | 处理 | 回执里怎么写 |
|---|---|---|---|
| 病例库里没有这个就诊 | 新增 | 建就诊和第 1 版 | 新增 N 次就诊 |
| 有，内容指纹相同 | 不变 | 不建新版本 | 不变 N 次 |
| 有，内容不同 | 更新 | 建新版本，旧版本保留，列出变化摘要 | 更新 N 次（体征多了 12 条、检验改了 3 个值…） |
| 病例库里有、这次文件里没有 | 不处理 | 不删 | 提示：本次文件不含既往 N 次就诊 |
| GD式：病案号相同、锚点日期差 ≤7 天（锚点由数据算出，补了早期记录会挪） | 疑似同一次住院 | 默认按更新；预览里可改为"另一次住院" | 逐条列出 |
| 同一个文件里同一个就诊编号出现两组 | 问题 | 这两组都不导入，进问题清单 | 列出行号 |

**撤销**：研究者可撤销任何未冻结的导入，医生可撤销自己 7 天内的导入；撤销后受影响的就诊回到上一个版本，没有上一个版本的就诊整体移除。更正不删，按记录指纹重新挂接，挂不上的进问题清单。

**更正**：医生在病例详情里改值，必须写原因；原值保留，病例上显示"已更正"和更正记录；冻结（§3.8）过的数据不能改，要改先由研究者解冻并留痕。

**原始文件归档**：每个导入的文件按 sha256 存在数据区 `archive/`，与病例库一起备份；回执和病例详情可以下载原文件。预览而没有确认的导入，读取结果 24 小时后清掉，导入记录留着（状态"未确认"）。

**为什么放数据库，不再放运行目录的 Parquet**：病例库要逐次累加、逐值更正、按中心查，数据库合适；规模不大（现有三类来源约 6 万条记录、6 千份病历，十个中心也在百万行以内）。Parquet 只用于冻结快照和导出。目前计划文档显示首次真实运行（旧计划待办 9–12、20）还没做；如果 `data/flucase_var` 里已经导入过真实数据，按新流程重新导入即可，原始文件都在。

### 3.4 格式体系

| 层 | 是什么 | 谁来建 | 例子 |
|---|---|---|---|
| 格式族（代码） | 一类表结构的读法 | 开发（Claude） | CRF 宽表族、EHR 多表族、一行一次就诊族、长表族 |
| 格式（配置，带版本） | 某种导出的具体写法：工作表、表头行、列怎么找、编码值的含义、已知笔误 | 内置；研究者在页面上建 | GD式 v1、GAM式住院 v1、GAM式门诊 v1、门急诊导出模板 v1、标准导入模板 v1 |
| 相似格式 | 同一族、与已有格式只差列名、列序、工作表名、增删列、编码写法 | 页面上"确认差异"后存成新格式，注明"基于 GD式 v1" | 某中心按同一份 CRF 填的表，多了一列 BNP、性别写"男 / 女" |
| 格式向导 | 认不出的 Excel / CSV | 现在的通用导入扩展而来 | — |
| 标准导入模板 | 系统按数据字典生成的 Excel 模板，带下拉和中文说明 | 系统 | 发给格式实在对不上的新中心 |

**认格式**：每个格式给出符合度和差异清单。

- **完全符合**（必需结构都在、表头全部认出）：直接读取；
- **相似**（同一族的必需结构都在，差异只在列名、列序、工作表名、增删列、编码写法）：进"格式差异确认"——缺的列指定是哪一列或标"本院没有"，多的列指定对应哪个数据项或忽略，改了名的列系统按别名猜好请人确认，编码值（如性别写 1 / 2 还是男 / 女）确认含义；确认后存成新格式；
- **认不出**：进格式向导；或者下载标准导入模板，让中心按模板整理。

"必需结构"按族定义：CRF 宽表族要有两行表头、病例ID列、年龄列（续行分组靠它）；EHR 多表族要有就诊编号列，以及检验、病历两张表至少一张；一行一次就诊族要有就诊编号和就诊时间。

**版本**：格式用过以后不能改，改动存成新版本；每次导入记下用的格式版本和读取器版本，旧导入可以复现。

**一个现成的相似格式例子**：服务器 `export_crf_excel.py` 导出的医院版 CRF Excel（Sheet1 + 合并症 + 说明 + 变量字典）现在被识别规则特意排除（`align.GD_EXPORT_SHEETS`）。新设计里它就是 GD式的相似格式，可以直接导入。注意它里面是化名，和同一中心的原始导出同时导入会出现两套编号的重复病例，同一中心只导其中一种（§7 第 15 项）。

| 诊断病史第 9、11 列没有表头 = 体格检查、医嘱建议；病历信息的"处方号"列实为就诊类型；检验第 11 列没有表头 = 异常标记 | legacy；**新**：写进格式配置 |
| 一次就诊一条（关联字段）；检验、体征（体格检查）、症状（主诉 + 现病史）、处方、检查 | legacy `_build_op` |
| 门诊没有年龄、性别：病例库把它挂接到同一病人的住院后补上，标"取自住院记录"；没有住院的，年龄、性别记"未记录"，回执里说明 | **新**（原来只在三件套对齐里一次做） |
| 门诊挂接住院（同一病人、就诊在入院前 0–14 天）放到病例库层（§3.6） | legacy 规则 + **新**位置 |

读取器的共同要求：

- 遇到不认识的写法不报错退出，记成带位置的问题，能读的照常读；
- 每个值带来源（文件、工作表、Excel 行号、列字母、表头、原值）；
- 病历正文照常交给规则抽取（S5），本地 LLM 第二抽取仍按 `FLUCASE_LLM` 开关；
- 不依赖 pandas 的具体大版本：在 pandas 2、3 上都跑测试（旧对齐代码要锁 pandas 2.x，移植后不再需要）。

### 3.6 跨文件挂接放在病例库里做

文件可以分开、分批导入，所以"门诊 ↔ 住院"这类关系不能在单个读取器里算。每次导入确认后，对涉及的患者重算一遍挂接：

- GAM：同一病人ID，门诊就诊在入院前 0–14 天 → 挂到那次住院；补门诊的年龄、性别；记"入院前门诊已检出流感"；
- 门急诊的随访（O3 用）：门诊之后的住院、死亡；
- 挂接规则写在中心的配置里，换中心可以换规则；每条挂接记规则和时间差。

### 3.7 问题清单

| 级别 | 含义 | 例子（完整代码表见附录 B） |
|---|---|---|
| 不能导入 | 整个文件读不了 | 文件打不开；认不出格式；找不到病例ID列 |
| 这一行没导入 | 某些行跳过，其余照常 | 病例ID为空；像续行但上面没有患者第一行；同一个就诊编号出现两组 |
| 请确认 | 导入了，但系统做了判断或改动 | 日期像是年份写错（已修正）；数值超出合理范围（保留原值，不参与分级）；单位不明；勾选了治疗但没有开始时间；检验项目没有对应的数据项 |
| 提示 | 知道一下即可 | 续行病案号被下拉递增（已忽略）；"<0.05"按 0.05 记；这些列没有导入；门诊记录没有年龄性别（导入住院后自动补） |

每条问题都写：在哪里（文件、工作表、第几行、哪一列）、原值、系统怎么处理、你可以怎么做（改原表后重新导入 / 在系统里更正 / 确认无误 / 忽略并备注）。处理完计数随之变化，首页显示还剩多少。

### 3.8 下游功能怎么接病例库

| 功能 | 现在 | 改为 |
|---|---|---|
| 分级 | 每次运行的 S7 | 病例有变化（导入、更正、复核）就对这个病例自动重算；换规则集时全库重算；结果按（就诊版本, 规则集版本）存 |
| 复核、全字段标注 | 按运行生成条目，判定按记录编号叠加 | 按病例生成，判定按记录指纹叠加；病例更新后，没完成的条目重新核对证据是否还在 |
| 质控 | 当前运行，小格抑制 | 病例库，可以按中心、按导入筛；系统内不抑制 |
| 冻结与导出 | std_v1（含 CDM 对齐层） | std_v2：病例库快照（患者、就诊、记录、病历、分级、候选结局、复核、更正、数据字典、manifest），可复现；另有给医生的本中心统一格式 Excel |

### 4.3 用语规范

### 4.4 角色与中心

| 角色 | 谁 | 能做什么 |
|---|---|---|
| 研究者 `admin` | 你 | 全部；中心与账号；格式库；全部中心的病例；分级、复核、质控、冻结导出 |

## 附录 A 格式配置示例（GD式，节选）

只写表头和规则，不含数据；实际字段名以阶段 2 的实现为准。

```yaml
format: gd_crf
name: GD式 CRF 宽表
family: crf_wide
version: 1
detect:
  sheets_all: [Sheet1, 合并症]
  header_codes: [DEM002, VS001, LAB001, SYM001, TRT001, IMG001, OUT001, COM001]   # 认出比例 = 符合度
sheets:
  main: {name: Sheet1, header_rows: [1, 2], data_from: 3}            # 两行表头：模块行 + 字段行
  complications: {name: 合并症, header_rows: [1, 2], data_from: 3}
group:
  new_patient_when_filled: 年龄                                      # 年龄非空的行开始一位新患者
ids:
  patient: {column: 病案号, normalize: [strip_leading_zeros, upper]}
  encounter: [patient, anchor_date]                                 # 病案号-锚点日期（D37）
  same_encounter_within_days: 7
columns:                                                            # 按表头找列：先认编码前缀，再认别名
  age: {code: DEM002, aliases: [年龄]}
  sex: {code: DEM003, aliases: [性别], values: {"1": 男, "2": 女}}
  vaccine: {code: DEM005, values: {"1": 已接种, "0": 未接种, "9": 不详}}
blocks:                                                             # 一个时间列 + 一组变量
  vitals:   {module: 生命体征,       time: 记录时间, codes: "VS\\d{3}"}
  labs:     {module: 实验室检验结果, time: 记录时间, codes: "LAB\\d{3}"}
  symptoms: {module: 症状,           time: 记录时间, codes: "SYM\\d{3}"}
treatments: {codes: "TRT\\d{3}", fields: [开始时间, 结束时间, 剂量, 具体治疗]}
fixes:                                                              # 已知笔误
  duplicate_code: {TRT009: {ECMO: TRT009, 其他治疗: TRT010}}
  header_typo: {ECOM: ECMO}
complications_sheet:
  flag_codes: "CLP\\d{3}"
  attributes: [诊断时间, 判定依据, 严重程度, SOFA评分, DIC评分, 程度]
  blank_means: negative                                             # 研究者 10-01 定
```

相似格式只改这份配置，例如某中心性别写"男 / 女"：`values: {男: 男, 女: 女}`；多一列 BNP：在 `blocks.labs` 里加一条对应。
