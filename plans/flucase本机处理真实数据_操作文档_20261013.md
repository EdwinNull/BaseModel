## 1 先读：本机处理真实数据的规矩（D34）

1. **只拷化名后的 CDM。**化名对照表 `data/real_world/_pseudonym/registry.csv` 和原始导出（两家医院的 xlsx）不出服务器。这样本机的数据无法单独还原到真人。
2. **放在仓库外的受保护目录**（§3.1）：加密盘或加密目录；只有本人账户能读；不放 OneDrive、iCloud、Dropbox、坚果云等同步目录。
3. **不进任何仓库**：BaseModel 和 flucase 的工作目录里都不放真实数据，也不放从真实数据导出的逐例文件。
4. **不传任何在线服务**：不上传网盘，不发邮件，不粘贴进任何在线大模型（包括 Claude）。
5. **Claude 不读真实病例内容**：本机用 Claude Code 时，先按 §3.4 设好读取限制。涉及真实数据的命令由你自己执行；需要 Claude 帮忙时，只告诉它计数、列名、报错类型，报错信息里的病例取值先删掉（§7）。
6. **文档只放聚合量**：报告里 1–9 写作 <10，不写任何病例编号以外的逐例信息。

服务器上 `data/real_world/README.md` 和 `aligned_cdm/README.md` 原来写着"不得复制到 W 之外"。10-13 已在两份 README 的隐私提示里各补一行 D34 例外：化名后的 CDM 可以拷到研究者本人设备处理，原始文件和化名对照表仍不得拷出（备份与日志在 `W/logs/2026-10-13/`）。

## 4 第一阶段开发：让 flucase 读 CDM、导出标准格式（交给 Claude Code；待办 4–8）

在 BaseModel 目录开 Claude Code 会话，开场白：

> 按 `plans/flucase本机处理真实数据_操作文档_20261013.md` 第 4 节做。只用虚构数据开发和测试；不要读取 `~/flucase_real` 下的任何文件；需要知道 CDM 的结构就看 `flucase/backend/flucase/pipeline/adapters/cdm_v31/` 里的两份字典。在 flucase 新建分支做，做完给我看测试结果，我同意后再合并到 main。

开发内容与验收（每项都要有测试）：

**1. 虚构 CDM 样例**（`flucase/synth/cdm_v31.py`）

- 按两份字典生成 9 张表的 Parquet，列名、类型和真实 CDM 一致，取值全部虚构；另生成 `run_meta.json` 和 `SHA256SUMS`，格式同真实目录。
- 规模小一些：GD_CRF 约 40 次、GAM_IP 约 30 次、GAM_OP 约 60 次；GAM_OP 里有一部分通过 `linked_ip_encounter_id` 关联到 GAM_IP。
- 化名用一看就是虚构的格式，例如 `DEMO-GDE0001`、`DEMO-GAME0001`、`DEMO-GAMV0001`。
- 文书（`notes`）用现有虚构文书生成器的写法，不复制任何真实文本。

**2. CDM 适配器**（`pipeline/adapters/cdm_v31.py`）

- 输入是一个 CDM 目录（9 张 Parquet + 字典 + `run_meta.json`）；识别靠文件组合与 `run_meta.json` 的版本号。
- 校验：每张表的必有列都在；按来源报计数（就诊、各类记录）；时间、精度字段能解析；只出计数，不出逐行内容。
- 一个 CDM 目录建三个批次与三条运行（GD_CRF、GAM_IP、GAM_OP 各一），沿用"每个来源一条当前运行"的现有逻辑。
- **不再化名**：就诊编号、患者编号直接用 CDM 里的；flucase 自带的化名（会编成 `DEMO-` 开头）对 CDM 输入关闭。
- 映射：
  - `encounters` → 就诊：预测时点取 `anchor_time`（取法 `anchor_rule`、精度 `anchor_precision`），年龄、性别、BMI、死亡及时间、离院时间、基础病 `COM001–COM010`、疫苗 `vaccine_code`、流感检测（`flu_test_pos` 等）→ 相应抽取记录。
  - `events` → 体征、检验、症状记录（数值、`unit_cdm`、时间、`time_precision`、`time_kind`；`implausible`、`censor` 记为标记）。
  - `treatments` → 治疗记录（状态、起止、时间来源）；`complications` → 并发症记录；`imaging` 的报告结论能用的就用。
  - `notes` → 文书，交给规则抽取（S5）。若 `notes` 没有书写时间，文书抽取的时间记"未知"，并在校验结果里报出来（计划 §6）。
  - `outcome_components`、`crf_view` 不参与分级，只用于核对。
- GAM_OP 按门急诊来源处理（场景 `ed`）；`linked_ip_encounter_id` 与关联住院的时间 → "随访：住院"记录，供 O3 使用（D32：只是候选结局）。
- 前端的来源名称补上：GAM_IP"广安门住院"、GAM_OP"广安门门诊"。

**3. 正式模式补齐**

- 建账号命令：`python -m flucase.admin create-user <用户名> --role admin`（密码用交互方式输入，不出现在命令行和日志里）；另有 `list-users`。
- 不灌演示数据：加环境变量（例如 `FLUCASE_SEED_DEMO=0`），正式模式默认不灌。
- 本机 http 登录：正式模式的会话 Cookie 现在强制 HTTPS，本机 `http://localhost` 可能登不上。加开关（例如 `FLUCASE_COOKIE_SECURE=0`），只在本机使用时关；在服务器上经 SSH 隧道访问时也用这个开关，并写进 README。
- LLM：加显式开关（例如 `FLUCASE_LLM=off|preset|local`）。真实数据的运行一律 `off`（D33），运行记录里写明。
- 复核条目照常生成，不自动分派（D33）。

**4. 标准格式导出**（计划 §3；`flucase/export/std_v1.py` + 命令 `python -m flucase.export --snapshot <编号> --out <目录>`，质控页冻结快照处加"导出标准格式"按钮）

- 对齐层：原样带上 CDM 的 9 张表和两份字典（或只记版本与 sha256，二选一，按导出大小定，写进 manifest），加 `facts` 表（每条抽取记录：方法、规则号、证据位置、复核状态）。
- 分析层：`encounters`、`observations`、`severity_timeline`、`outcomes`、`review` 五张表，列见计划 §3.2。
- `manifest.json`：版本号 `std_v1_<日期>`、生成时间、输入 CDM 版本与 sha256、规则集版本、映射版本、flucase 提交号、复核截止时间、各表行数、隐私审计结果、每个文件的 sha256、处理地点。
- 数据字典（每列的含义、类型、单位、取值、缺失怎么表示、时间精度、来源）和质控摘要（只含聚合量，1–9 写作 <10）。
- 可复现：同一输入、同一版本，数据文件的 sha256 不变（行按固定键排序；manifest 自身含生成时间，不参与比较）。
- 导出后自动过一遍隐私正则（姓名、号码、电话、身份证、住址等），命中不为 0 就不写出。
- 医院版 CRF Excel 不在 flucase 里做：继续用服务器上的 `export_crf_excel.py`。

**5. 测试与合并**

- 在虚构 CDM 样例上跑通导入 → 运行 → 冻结 → 导出；导出两次 sha256 相同；隐私正则 0 命中。
- 原有测试全部通过；`npm run typecheck`、`npm run build` 通过；`python scripts/scan_identifiers.py` 0 命中。
- 更新 flucase README 和 `docs/design.md`；在 flucase 新分支提交，研究者同意后合并到 `main` 并推送。

## 7 出问题怎么办

- **请 Claude 帮忙时只给聚合信息**：报错的类型和行号、出错的表名和列名、计数；把报错信息里的病例取值（姓名、编号、日期、数值、文书片段）删掉或换成"<值>"再贴。
- **常见问题**：

| 现象 | 先查 |
|---|---|
| 正式模式登录后又跳回登录页 | 是否设了 `FLUCASE_COOKIE_SECURE=0`；是否用 `http://localhost` 访问 |
| 启动时报端口被占用 | 换端口，例如 `--port 8001` |
| 识别与校验报"缺少列" | 对照 §3.5 的列字典看缺的是哪一列；可能是 CDM 版本不同，看 `run_meta.json` 的 `version` |
| 计数与 `run_meta.json` 对不上 | 看校验结果里每类记录被跳过的条数和原因 |
| 导出被隐私正则拦下 | 看命中的是哪一类规则、哪张表哪一列，只把这三样告诉 Claude |
