## 0 一页结论

- **现状**：服务器上已经有一条处理真实数据的流水线：对齐代码 `basemodel/alignment/` 把原始导出变成统一数据模型 CDM v3.1，`scripts/export/export_crf_excel.py` 再按广东省中医院 CRF 原表版式导出 Excel。flucase 有分级、复核、全字段标注、质控和冻结快照，但只在虚构数据上跑过。两边没有接起来。
- **路线（D30）**：分两步接，不在 flucase 里重写对齐。
  1. 第一阶段：flucase 直接读已经对齐好的 CDM v3.1，在上面做分级、复核、质控和标准格式导出。
  2. 第二阶段：新导出到了以后，flucase 在服务器上原地调用对齐流水线：放入原始文件 → 对齐成新版本 CDM → 接着走第一阶段的流程。对齐代码留在服务器上，不搬进 flucase 仓库。
  - **D36（10-13）修改第 2 步**：对齐代码在人工检查后原样引入 flucase（`legacy/`），flucase 在研究者设备上也能直接处理原始 Excel：原始 Excel → CDM v3.1 → 第一阶段的流程 → std_v1。最终产出就是 std_v1；医院版 CRF Excel 仍在服务器上生成。
- **在哪里处理（D34、D35）**：数据使用协议允许研究者在服务器外的本人设备上处理真实数据。D35 取消"原始数据不出服务器"：原始 Excel、化名对照表和 CDM 都可以放在研究者设备上 BaseModel 的 `data/`（已 gitignore）里，由 flucase 处理；化名沿用服务器的 `registry.csv`，与 CDM 和实验一致。flucase 在服务器上的部署（D31）留到复核医生需要访问时再做。
- **标准格式（D29）**：三层，以 CDM 为准：① 对齐层（CDM，v3.1 扩为 v3.2）；② 分析层"标准病例数据集"（从 ① 派生）；③ 展示层"医院版 CRF Excel"（已有）。
- **时间（估计）**：第一阶段约 1.5–2 周（按 D11，医院线占 30–40% 时间）；文本抽取的校准等复核医生（11 月）；第二阶段等新数据。

## 3 标准格式（D29）

### 3.1 三层

| 层 | 用途 | 形式 | 内容 | 谁用 |
|---|---|---|---|---|
| ① 对齐层：CDM v3.2 | 统一编码、单位、时间，其余一切的基础 | 每张表一个 Parquet + 列字典 + 变量字典 | v3.1 的 9 张表原样保留；新增 `facts` 表：flucase 的抽取记录，带方法（结构化 / 规则 / LLM / 复核）、规则号、证据位置（文书编号与字符区间，或原表单元格） | flucase、实验 |
| ② 分析层：标准病例数据集 v1 | 描述分析和建模直接读 | Parquet + 数据字典 + manifest | 见 §3.2 | 实验（`rw_gam2gd`）、统计 |
| ③ 展示层：医院版 CRF Excel | 给医院方核对对齐结果 | xlsx，广东省中医院 CRF 版式 | 沿用服务器上的 `export_crf_excel.py`，不重写 | 医院方 |

### 3.2 标准病例数据集 v1 的内容

只放已定口径能确定的东西；时间窗、特征怎么取由实验配置决定（A 档），不在数据集里写死。

| 表 | 粒度 | 主要列 |
|---|---|---|
| `encounters` | 每次就诊一行 | 化名（患者、就诊）、来源、场景（住院 / 门急诊）、年龄、性别、BMI、预测时点及其精度与取法、起病日期及来源、发病到就诊天数、发热三态、病原学确诊（三态）、基础病与疫苗（有 / 无 / 未记录） |
| `observations` | 每条观测一行 | 变量编码、数值、单位、时间、时间精度、相对预测时点的小时数、来源（结构化 / 规则 / LLM / 复核）、是否在复核后改过 |
| `severity_timeline` | 每段分级一行 | 级别、起止时间、判据、判据类、证据编号 |
| `outcomes` | 就诊 × 候选结局 × 判据类 | D0、O1、O2、O3、O3 的 7 天窗；主口径、生理类、三类合并；取值（事件 / 不干净事件 / 未知 / 排除 / 无事件）、事件时间、规则集版本、自动层或有效层 |
| `review` | 每条复核覆盖一行 | 条目类型、字段、结论、来源（单人 / 两人一致 / 共识）、复核截止时间 |

每个导出包都带：

- `manifest.json`：数据集版本号；生成时间；输入（CDM 版本及其 sha256）；规则集版本；映射字典版本；flucase 代码提交号；复核截止时间；各表行数；隐私审计结果；每个文件的 sha256；处理地点（服务器 / 研究者设备）。
- 数据字典：每一列的含义、类型、单位、取值范围；缺失怎么表示（未记录、阴性、未评估分开）；时间精度；两院原字段来源（从 CDM 变量字典继承）。
- 质控摘要：只含聚合量，1–9 写作 <10。
- 数据使用台账一行（flucase 已有）。

### 3.3 规矩

- 逐患者的导出放在处理它的那台机器的受保护目录里：研究者设备上放在 BaseModel 的 `data/`（已 gitignore，操作文档 §3）；服务器上放 `basemodel/derived/flucase/exports/<版本>/`（700/600）。两处都不进任何仓库，不传任何在线服务。
- 版本号形如 `std_v1_<日期>`，旧版本不删；同一输入、同一版本，导出的 sha256 必须相同。
- 实验要用的导出拷回服务器 `basemodel/derived/flucase/exports/`，再由实验读取，保证实验输入可追溯。
- 候选结局一律带"候选"和规则集版本；用哪一列做标签由研究者定（A 档）。

## 5 数据纪律与 Claude 的参与方式

- D35 起，研究者设备上可以有原始 Excel、化名对照表 `registry.csv`、CDM 及其导出（取代 D34 的"只拷化名后的 CDM"）。本机数据因此能直接对应到真人，下面几条都要守住。
- 本机真实数据只放在 BaseModel 的 `data/`（`.gitignore` 已排除；目录只给本人，整盘加密）：不放进 flucase 目录或其他仓库，不放云同步目录，不传任何在线服务（含在线大模型）。
- 化名只有一份口径：本机用从服务器拷来的 `registry.csv`，只为新患者追加；只在一处追加，追加后同步到另一处。
- Claude 不读任何真实病例内容：不打开、不打印真实数据目录里的文件。另一台设备上的 Claude Code 要先设好读取限制（操作文档 §3.4）。开发和测试只用虚构 CDM 样例；涉及真实数据的命令由研究者执行，只把计数、列名、报错类型这类聚合信息告诉 Claude，报错信息里的病例取值先删掉。
- 真实文本上的规则改进只靠三样：全字段标注的逐字段评测；按规则统计的命中数；研究者看了漏抽的病例之后，用自己的话描述写法（不粘贴原文）。
- 对齐代码在研究者完成人工检查（后续工作计划 §3.3、操作文档 §4A 第 0 步）之前，Claude 不读源码。10-13 Claude 只在服务器上跑了只出计数的扫描（标识符 0 命中，中文长片段 78 处），没有看代码内容。

## 6 风险

| 风险 | 对策 |
|---|---|
| 真实文书的写法与虚构数据差别大，第一次运行文书抽取的召回率可能很低 | 第一阶段以 CDM 里已经结构化的记录为主，文书抽取作补充；第二阶段评测后再改 |
| CDM 的派生列（`derive.py` 的候选列、`outcome_components` 的三态）与 flucase 分级口径不一致 | 核对表逐项解释；分级以规则集为准；`derive.py` 的列只作对照 |
| 化名不一致，结果与实验对不上 | 一律沿用 CDM 化名，flucase 不再化名 |
| CDM 的 `notes` 表若没有书写时间，文书抽取的时间只能记"未知" | 开发前按字典核对；需要的话在对齐流水线里补，作为 CDM v3.2 的改动 |
| 研究者设备丢失或被他人使用 | D35 起本机有原始数据和化名对照表，能还原到真人：整盘加密，`data/` 只给本人账户，用完的中间产物按操作文档 §6 清理 |
| 真实数据被误提交 | BaseModel 的 `.gitignore` 排除 `data/`；真实数据不放进 flucase 目录（另一个仓库，不排除）；flucase 提交前钩子扫描标识符 |
| 化名对照表在本机和服务器两处各自追加，同一个号指向不同的人 | 新数据只在一处对齐；追加后立即同步到另一处，并核对两处 sha256（操作文档 §1 第 4 条） |
| 本机对齐结果与服务器不一致（代码版本、依赖版本不同） | flucase `legacy/` 与服务器 `alignment/` 的 sha256 一致；本机对齐结果与 20261001b 核对（待办 19）通过后才用原始 Excel 这条路 |
| 新数据和临床回复的时间都不确定（D27） | 第一阶段只用现有数据；口径仍是候选，换版本号重算即可 |
